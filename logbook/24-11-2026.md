## Hari ke-6: Pemahaman GPU Layer Offloading

**Target:** Memahami penyebab bobot model meluber (*spillover*) ke CPU/RAM, dampak penurunan kecepatannya, serta cara mengoptimalkan pembagian layer agar diproses maksimal di GPU.

### Ringkasan Konsep
* **Penyebab CPU Spillover:** Ketika total kebutuhan memori (**bobot model + KV cache + *compute buffer* + beban tampilan OS**) melebihi kapasitas VRAM bebas GPU (batas aman `~3.200 MiB` pada RTX 3050 4 GB), Ollama otomatis memecah model dan melempar sisa layer *transformer* ke RAM sistem untuk dikerjakan oleh CPU. Karena *bandwidth* RAM sistem dan jalur PCIe jauh lebih lambat daripada memori VRAM GPU, kecepatan generasi token (*decode*) langsung anjlok.
* **Flash Attention (`OLLAMA_FLASH_ATTENTION=1`):** Teknik optimasi komputasi *attention* yang hemat memori dengan memecah matriks perhitungan menjadi blok-blok kecil (*tiling*) sehingga tidak memakan lonjakan VRAM sementara saat menghitung skor *attention*, sekaligus menjadi syarat wajib untuk mengaktifkan kuantisasi KV cache.
* **5 Cara Mengatasi GPU Offloading & CPU Spillover:**
  1. **Kuantisasi KV Cache (`OLLAMA_KV_CACHE_TYPE=q8_0`):** Memadatkan penyimpanan vektor Key dan Value dari `FP16` (2 byte) menjadi `Q8_0` (1 byte) sehingga ukuran memori KV cache menyusut hingga 50%.
  2. **Cegah Model *Reloading* (`keep_alive`):** Mengatur durasi `keep_alive` yang cukup (dan menghindari pemanggilan banyak model bergantian) agar model tidak berulang kali dibongkar-pasang (*unload/reload*) antara disk/RAM dan VRAM.
  3. **Sesuaikan Panjang Konteks (`num_ctx`):** Memangkas `num_ctx` (misalnya dari `4096` ke `2048` atau `1024`) untuk mengecilkan alokasi KV cache dan menyisakan ruang VRAM bagi layer bobot model.
  4. **Pilih Kuantisasi & Atur `num_batch`:** Menggunakan kuantisasi yang sesuai kapasitas VRAM (misalnya `Q4_K_M`) dan mengecilkan `num_batch` (default `512` $\rightarrow$ `128`/`256`) jika perlu menekan ukuran *compute buffer* sementara saat fase *prefill*.
  5. **Kunci Jumlah Layer GPU (`num_gpu`):** Mengatur `num_gpu` secara eksplisit sesuai total layer model agar seluruh blok *transformer* dipaksa masuk ke GPU ketika mode `auto` Ollama terlalu konservatif.

### Analisis Hasil Pengujian
1. **Efek Tebing (*Cliff Effect*) pada Kecepatan Decode:** Selama masih ada sebagian layer *transformer* yang tertinggal di CPU, GPU terpaksa menunggu CPU menyelesaikan bagiannya pada setiap token. Pada `qwen3:4b`, memindahkan 50% layer ke GPU (`18/36` layer) hanya menaikkan *decode* dari `7,2` menjadi `10,6 t/s`, tetapi begitu ke-36 layer dipaksa masuk ke GPU (`num_gpu=36`), kecepatannya melompat **3,09x** menjadi **`48,8 t/s`**.
2. **Kenapa `% GPU` Maksimal Berada di ~76–87% (Bukan 100%)?** Parameter `num_gpu` hanya memindahkan blok layer *transformer* utama ke VRAM, sedangkan tabel *token embedding* dan *output head* tetap ditaruh di RAM sistem agar VRAM tidak penuh. Karena seluruh blok layer *transformer* sudah di VRAM, kecepatan tetap mendekati performa penuh GPU sekaligus menekan pemakaian RAM sistem hingga turun **1,6 GB** pada `qwen3:4b`.
3. **Pemilihan Model Terbaik Kelas 4B:** **`qwen3:4b` (dengan `num_gpu=36`, `num_ctx=2048`)** adalah kandidat pengganti terbaik untuk tugas berat karena kecepatan *prefill*-nya paling tinggi (**`366,7 t/s`**) untuk memproses *system prompt* dan skema *tool* dengan cepat, sementara **`qwen3.5:2b-q4_K_M`** tetap dipertahankan sebagai model utama harian untuk konteks panjang (`4096–8192`) dan respons kilat (`84,0 t/s`).

### Kesimpulan
> CPU spillover adalah penyebab utama lambatnya inferensi lokal pada GPU ber-VRAM terbatas. Dengan mengombinasikan penyesuaian `num_ctx=2048` dan penguncian seluruh layer ke GPU (`num_gpu=36`), model kelas 4B seperti `qwen3:4b` dapat berjalan lancar di RTX 3050 4 GB dengan peningkatan kecepatan *decode* hingga **3x lipat** sekaligus menjaga pemakaian RAM sistem 8 GB tetap aman dari *paging*.
